# 自动选品工作台：技术架构

版本：v0.1｜2026-10-31，北京时间｜**待用户确认，不能据此启动开发或部署**。

## 1. 架构目标与已确认约束

- 云端持续运行，人员网页登录；没有本地服务器，不依赖电脑常开。
- 极鲸云 API 是持续数据源；已取得的 22,664 件美国站样本用于初始化，不是人工导入型产品。
- 每天自动执行一次发现与更新，允许人员手动发起研究；精确时间、预算、更新对象规模尚待确认。
- 批量发现和指定商品分析并存；标品与差异化/POD 两条机会线并存，允许一件商品归入多条机会线。
- AI 承担研究与判断，人定义规则和经营决策边界。选品流程后续随主管意见调整。
- AI 通过 OpenRouter 使用 GPT-6.1 Terra 与 Decisions；Amazon 优先 SP-API，已有非 PII 权限作为接入基础。

## 2. 推荐技术栈与生成器边界

| 领域 | 推荐选择 | 原因与边界 |
|---|---|---|
| 工程 | TypeScript strict、pnpm workspace | 同仓维护模块、统一依赖与类型 |
| 页面 | React SPA、TanStack Router/Query | 商品列表、筛选、任务与研究详情 |
| UI | shadcn/ui、统一样式 token | 基础组件复用，产品视觉独立设计 |
| 接口 | Hono、oRPC、边界结构校验 | 类型共享，页面与业务实现解耦 |
| 运行 | Cloudflare Workers | API 与后台任务均云端执行；Node 只用于工具链，不假定 Node 内建库在生产可用 |
| 部署 | 官方 Wrangler 与显式配置 | 应用 Worker 与任务 Worker 独立部署，避免以预览部署工具作为关键依赖 |
| 存储 | D1、版本化 SQL migrations | 首期使用原生 SQL，仓储接口控制耦合；有索引和保留策略 |
| 归档 | R2 | 原始 API 响应、较大结果和证据；数据库保存引用 |
| 调度 | Cron Triggers + Workflows | 一天一轮，分步骤持久执行与恢复；只有吞吐证据支持时才增加 Queues |
| 身份 | Cloudflare Access + 应用角色 | Access 验证入口身份，应用验证 JWT 并管理操作权限 |
| 质量 | Vitest、Playwright、Knip、Ultracite | 关键业务与跨模块流程验证；具体版本创建时固定 |

VibeStart 0.1.3 已完成 help、list 与 dry-run；SPA/Hono/oRPC/Workers/Void/no-database/no-auth 组合解析成功，预计 71 文件，**项目尚未生成、安装或测试**。该版本没有 D1 选项，SQLite 模板是 node:sqlite；Void 标记预览。该成功预览不能证明 Wrangler 部署、D1 或 Workflows 已跑通。

工程创建前需做一次 Cloudflare 兼容性验证：优先由 VibeStart 生成匹配的前端和共享基础，再建立 Hono Workers 后端及 Wrangler 配置；可单独使用前端生成方案，避免先生成 Node 后端再冒称 Workers。对生成器管辖选项通过 CLI 维护，不伪改 vibestart.jsonc。最终 recipe、版本、脚手架文件归属应记录。若 CLI 没有合法组合覆盖目标，不为迁就模板改用外部数据库，由用户评审新增方案。

## 3. 模块化单体与部署单元

同一代码仓库、共享领域包，两个 Worker 部署单元：api 处理短请求、权限与任务创建，jobs 处理 Cron 和 Workflows。不是两套互相调用的独立业务系统；它们共享应用服务，通过任务 ID 协同，不通过前端维持任务。

| 模块 | 职责 | 不负责 |
|---|---|---|
| sources | 极鲸云/SP-API 鉴权、限流、计费、响应转换 | 选品推荐 |
| catalog | 平台商品、规格、当前快照、历史及关联 | 调用模型 |
| discovery | 类目/关键词搜索策略、新品与更新集合 | 经营决策 |
| tracking | 关注清单、更新频率、缺失与状态观察 | 将搜索未命中直接当下架 |
| ai | Terra 与 Decisions 适配、提示词版本、调用成本 | 直接扣 API 预算或任意执行 |
| research | 研究任务、同类聚合、比较、证据与机会报告 | 直接访问供应商 SDK |
| candidates | 标品/POD 标签、观察池、审核与反馈 | 自动上架 |
| jobs | 步骤编排、租约、预算、重试、暂停与恢复 | 写死评分公式 |
| identity | 身份、应用角色、审计 | 自建密码系统作为首期前提 |

## 4. 数据流与业务流

日任务：读取已发布策略版本 → 取得运行租约 → 预留预算 → 按类目/关键词分页发现 → 标准化与去重 → 更新当前快照并追加观测 → 生成研究对象 → Decisions 分流 → Terra 研究重点对象 → 写入候选/观察池 → 汇总本轮新增、更新、错误与费用。

指定商品：解析名称/链接/图片 → 解析或搜索候选 → 用户选择或系统明确匹配 → 查询详情/历史 → 同类与跨平台研究 → 生成报告与人工反馈入口。可以从链路中间启动，不必先扫完整商品库。

22,664 件历史测试样本按平台+站点+商品ID初始化，来源标注为 bootstrap；保留供应商时间和实际请求时间，不伪装成上线当日采集。后续页面查数据库，后台从 API 持续补充。每日不等于逐件查完全部详情：批量搜索承担广泛更新，详情/历史用于重点对象；覆盖率需展示。

异常分支：鉴权失败停止受影响连接；余额不足或预算不足暂停；限流遵循退避并暂停该来源，不换 key 绕过；超时保留费用不确定记录；缺字段降级分析；未获取到数据不写零；重复任务复用成功步骤；无法匹配进入人工确认。

## 5. 数据边界

平台商品唯一键为 provider-independent 的 platform+market+externalProductId；SKU 单独识别。跨平台同款关联带 method、证据、状态与人工确认，不合并成同一平台商品。

核心实体：products、variants、observations、external_links、product_groups、research_runs、research_results、candidates、feedback、job_runs、job_steps、usage_reservations、usage_events、strategy_versions、prompt_versions、audit_events。确切表结构在开发前设计。

observations 分离 observedAt、fetchedAt、periodStart/End、currency、metricDefinition、estimationStatus。供应商只给 updateTime 时原样保留，不能冒称真实观测时间。不同口径的累计销量与估算月销不能拼成一个指标。R2 原始证据使用不可变对象键；D1 保存清洗结果和引用。

## 6. AI 链路

Terra（openai/gpt-6.1-terra）负责理解目标、提出搜索/补查动作、分析图片与规格、解释趋势、形成报告。Decisions（openai/gpt-6-luna-decisions）使用 OpenRouter 独立 /api/alpha/decisions 适配，负责有边界的分类、分流与优先级判断。接口不能共用普通聊天请求结构。

程序计算时间间隔、增长、去重和费用；模型不替代算术。可执行工具注册为有结构输入/输出的能力；执行层检查权限、预算、数据范围、取消状态。低证据/不确定结论进入观察或复核；模型概率不等于商业成功率。供应商标题、评论和网页内容视为数据，不能覆盖系统规则或要求泄露密钥。

每份分析关联输入快照、模型、提示词/策略版本、工具调用记录、结论摘要和费用；展示行动与证据，不要求输出模型隐藏推理。模型更换不覆盖旧分析。

## 7. 扩展和演进

新供应商实现 SourceAdapter；新模型实现 Research/DecisionAdapter；新研究步骤在 capability registry 注册；新流程引用已注册步骤。首期使用版本化代码编排加策略配置，不制作任意代码插件市场或通用拖拽引擎。

仓储层抽象业务查询而非伪造“通用 SQL”；D1→其他数据库仍需迁移、性能与一致性验证。随着历史增长，将原始/冷历史归档 R2，在线查询保留明确时间窗。逐步拆服务以实际瓶颈为依据，避免提前引入微服务、向量库或多套消息系统。
