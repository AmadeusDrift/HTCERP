# 美国站标题品牌词检查与存量复查 · P0 开发计划

本文件保留词库建设阶段的原始方案。v0.3 已完成后，ERP 实施以[海天城标题自查与在售巡检接入计划](2026-11-02-htcerp-title-audit-integration.md)为准，运营无需选择商品类别。

**目标**　运营能在上架前检查英文标题，也能在品牌风险变化后找到需要复核的老商品。单个美国店铺先试点，以抓住历史上的真实下架原因和控制误报为验收依据。

**实现方式**　人工预检、SP-API 同步、词库更新和每周复扫共用同一套匹配和分级规则。复用 TypeScript、Hono、React、现有 Jobs Worker、D1 和 R2。官方商标批量文件在已有可定时运行的机器上用 Python 流式处理。实施者可按 executing-plans 逐项执行，勾选下列验收项。

## 首个交付物：美国站标题品牌风险资料库 v0.1

先选一个在售类目，按下面的顺序交付可抽查的数据。运营能从每条规则找到原始依据以后，再把这版规则接入检查页。

| 顺序 | 动作 | 交付物与验收 |
|---|---|---|
| 1 | 收集外部资料。USPTO 查商标及其覆盖商品，亚马逊美国站查标题政策与官方用例，CourtListener/RECAP 查试点品类相关的公开案件并核对案卷。 | 外部资料表。每条保留来源、编号或链接、日期、原文要点和适用商品。案件记录权利类型以及申请禁令、获批或解除等已核实的进展。仅查到起诉或品牌同名时保留线索级别。[RECAP 公开档案](https://free.law/recap/) |
| 2 | 清洗外部记录。统一品牌拼写和别名，按申请号、政策出处或法院及案号去重。先核对权利人、商品和案件所涉权利，再关联不同来源。 | 可搜索的品牌资料卡。同名不同权利人分别保留；同一案件被多处转载只计一次。对缺少原文、涉及图片或无法确认与标题相关的资料分别标记。 |
| 3 | 加入本店案例。逐条录入整改前标题、商品与品牌、亚马逊通知原文、实际改动、恢复结果及授权依据；按品牌、商品、具体用法与外部资料关联。 | 店铺案例表。外部未收录的真实下架记录可独立保留。一次同时改了图片和标题、或通知未点明原因的记录，标为“原因未确认”。 |
| 4 | 把证据写成运营能执行的规则：哪个词、哪类商品、怎样写会触发、有什么例外、命中后核实什么。 | 第一版规则表。每条能回到外部资料或已核实案例；列出证据缺口。用预留案例盲测，公布漏掉的原标题和误报的整改版。通过后发布版本号，供新标题检查与老品回扫共同使用。 |

## 第一版的运营流程

| 场景 | 触发和范围 | 运营看到什么 |
|---|---|---|
| 准备上架 | 粘贴英文标题，选择本店品牌和商品类型即可检查；允许品牌未知 | 原文高亮、疑似第三方品牌、为什么提示、需要核实什么。编辑后可立即重查 |
| 已经上架或改名 | 美国站全商品报告建立底册，每 30 分钟拉一次新增和变更 | 新出现的风险进入同一个待办列表；注明店铺、SKU、ASIN、标题来源和检查时间 |
| 标题没改，外部情况变了 | 每天接收美国商标更新；运营可随时补录真实下架通知或有案号的公开案件线索 | 自动找到所有相关在售标题，说明哪条记录何时变化、谁需要重新处理 |
| 定期兜底 | 每天用全商品报告核对底册；每周错峰用最新词库和规则完整扫描一次在售标题 | 显示应扫、已扫、缺标题、失败和待补扫数量，可从失败批次继续 |

首版交付站内预检、待办和运行状态三个视图，可放在同一页面。运营负责在 Seller Central 核实和修改，系统重新取到实际标题后才标记整改完成。图片、外观专利和全美法院实时抓取留到后续；若案件或通知指向商品本身，待办引导运营把材料交给法务。正式法院通知单独置顶。

## 用什么数据，怎样控制成本

- **内部样本与外部资料对照。** 运营准备最近约 20 组整改前后标题，连同通知原文、日期、命中词、商品类型和恢复结果。在外部资料清洗后逐条关联，另记录本店自有品牌、授权范围和到期日。内部样本不足时明确列出尚未验证的规则。
- **以 USPTO 为官方底库。** 从 Open Data Portal 获取商标文字历史文件，再按发布日期补齐每日 XML。第 1 天实际验证账户、密钥、文件清单、历史覆盖截止日和日更接续日期。保留文字标记（含组合商标可检索的文字）、申请号、注册号、权利人、商品服务说明、类别、状态、记录日期和官方链接。用申请号更新，同名的多条记录分别存储。申请中、已注册、撤销及失效分别处理。关停或改名事件用旧词和新词都回扫一次。[官方批量数据说明](https://www.uspto.gov/trademarks/trademark-updates-and-announcements/trademark-bulk-data-us-patent-and-trademark-office) · [ODP 接入](https://data.uspto.gov/apis/bulk-data/search) · [官方每日数据目录](https://data.uspto.gov/bulkdata/datasets/trtdxfap)
- **试点类目先行。** 首批预检使用通过案例验收的规则表，明确显示“当前仅覆盖重点词”。后台批处理历史文件，按标准化首词散列分片，发布压缩词典到现有 R2，过大的分片再拆。保留发布清单、源日期、分片版本及校验值。发布完整版本前核对源文件连续性、状态分布，并抽查官方档案。持续更新需有现成定时机器及足够磁盘；机器离线时沿用最后完整版本，页面显示数据截至时间和延迟。
- **P0 商业检测采购预算为零。** 每次检查从自有词库查询。已有 D1、R2、Worker 和批处理机器按试点实际消耗核算。在 1 万条基准测试中记录读写行数、对象读写量、存储、CPU 与耗时，按现有账户剩余额度设置日预算。接近上限优先保障手动预检和高风险事件，常规复扫顺延并显示积压。报告记录“每万条新增基础设施费”和“外部检测费”两项，避免把免费数据等同于免费运行。

## 检查结果怎样判

| 发现 | 初始动作 |
|---|---|
| 命中本店历史下架词，且品类及错误用法相似；或商品把同类第三方品牌写成原厂来源，当前无适用授权证据 | 高优先级，给出原文、依据及核实动作。品牌出现在标题开头只是线索，需要结合商品实际品牌和商品类型 |
| 有效商标命中但属于常见描述词、用途或权利范围不清；新申请；仅发现同一品牌公开案件 | 进入观察或普通复核。查看商品服务说明、实际用法和案件所涉权利。普通词的自然描述用法减少提醒，保留命中证据 |
| 与第三方设备确实适配，标题清楚写出自家商品与适配对象；或有覆盖该店铺和商品的有效凭据 | 记录复核结果及适用范围。兼容词只适用于已核实的配件用途；印花、角色或品牌引流另行检查 |
| 数据源缺失、标题为空、最新版本尚未发布、词库查询失败 | 显示具体缺口并安排重试。检查成功且无命中时显示“本次未发现风险词”及覆盖范围 |

示例：假设 Acme 出售第三方保护套，`Kindle Paperwhite Case by Acme` 提示核实品牌归属；`Acme Protective Case compatible with Kindle Paperwhite` 在确有适配事实的前提下可降低优先级。保留匹配到的 Kindle 和审核理由。仅靠新增注册日期不能判定侵权。[亚马逊美国站兼容性标题示例](https://sellercentral.amazon.com/seller-forums/discussions/t/33ea36c2-06fc-42a0-8b28-4a6a6065bf72) · [USPTO 对侵权判断的说明](https://www.uspto.gov/page/about-trademark-infringement)

## 开发任务与顺序

相对于工作台项目根目录列出路径。现有 SP-API 适配器抽样最多 5 条，抽样入口继续供原业务使用。现有 Jobs Worker 每分钟调用调度器，新增任务在该调度器登记，仅在到期时领取。

**第 1 天 · 整理试点类目外部资料，再关联内部案例**

- [ ] 先完成前三张可审查的表（外部资料、店铺案例、规则），标出每条证据的来源和关联理由；在预留样本上完成首次盲测。其间可以验证店铺读取权限和容量，正式启用检查以规则验收为准。

- [ ] 从试点店铺主动请求 `GET_MERCHANT_LISTINGS_ALL_DATA`，记录市场、行数、状态、标题缺失率和报告生成耗时。抽查卖家 SKU、ASIN、标题和运营后台是否一致。验证 Listings Items 的增量权限；权限不全时允许导入运营手动导出的同格式报告以启动试点，标记“手动来源”。[全商品报告](https://developer-docs.amazon/sp-api/lang-us/docs/report-type-values-inventory)
- [ ] 在现有机器验证 ODP 下载与日更样本，测单个压缩包的处理速度、临时磁盘和可用空间。记录试点 SKU 总数、报告延迟、本地机器的定时可用性，与真实账户云额度一起作为排期条件。
- [ ] 给案例标注“误写品牌来源、真实适配、普通词、授权、通知原因不明”，按品牌或案例组分开规则开发和留出验收样本，整改前后两个版本放同一组。把卖家自查通知与法院文件分开记录。

**第 1–2 天 · 交付可用的手动预检**

- [ ] 新建 `workbench/packages/title-audit/match.ts`、`routes.ts` 和 `workbench/apps/web/src/title-audit.tsx`，分别负责匹配、权限校验和页面。在 `workbench/apps/api/src/index.ts`、`workbench/apps/web/src/main.tsx` 接入。提供 `POST /api/title-audit/preview`，输入标题、类目、店铺及声明品牌，返回命中区间、匹配词、级别、原因和证据。直接打开输入页即可使用，无需 ASIN。
- [ ] 匹配统一大小写、Unicode 和标点，支持词界、连字符、多个词组成的品牌及经核实的别名，保存标准化文本到原标题的区间映射。保留最长词组及不同权利记录。普通词按用法分级；商品类别相邻或未知时保留人工复核。证据缺失不自动认定授权。
- [ ] 新建 `workbench/migrations/0026_title_audit.sql`（实施时核对下一个可用编号）。保存店铺及美国市场、SKU、ASIN、标题版本、可售状态、品牌与类目、词与商品的映射、风险事件、处置证据、数据版本和任务进度。用词与商品的映射索引标题里出现的词，包括尚未被识别为品牌的词，供未来新注册品牌反查。授权按店铺、品牌、商品范围及有效期匹配。
- [ ] 手动预检优先使用已经发布的本地或缓存分片，同一请求内同一分片只读一次；采用有容量上限的缓存。记录词库版本和规则版本。发现源不可用时返回“待补查”，避免显示为零风险。

**第 2–3 天 · 接入完整的店铺标题和增量**

- [ ] 扩充 `workbench/packages/amazon/adapter.ts` 和 `request-pacing.ts`，在新文件 `workbench/packages/title-audit/sync.ts` 中实现“请求报告 → 后台轮询 → 下载解压 → 分批入库 → 核对行数”。每一步持久化进度。按店铺、市场和 SKU 去重；旧报告覆盖新标题前比较快照时间。只有完整成功的报告才可用于标记商品退出在售范围。空标题计入缺失并重试，数量异常的报告先复核。
- [ ] 每 30 分钟按固定时间窗和分页令牌调用 `searchListingsItems`，拉新建和有修改的商品，按标题及品牌、类目、状态等影响判断的字段判定是否重查。保留重叠窗口，整窗处理完成后再推进游标。达到结果上限时缩短时间窗，无法继续切分的时段标记缺口，用全商品报告对账；遇 429 按限流信息退避。[Listings Items 查询参数](https://developer-docs.amazon.com/sp-api/lang-en_EN/reference/searchlistingsitems)
- [ ] 保存卖家提交的标题与目录标题的来源标签。高优先级项目按需读取 Listings Items 属性及 Catalog Items 摘要；两者不同时并列展示，方便定位要更改的内容。授权失效时提示重新连接，单个店铺失败不阻塞其他任务。

**第 3–5 天 · 上线老品回扫、日更和运营待办**

- [ ] 新建 `workbench/scripts/build-us-mark-index.py`。流式解析 XML，在预处理机落 SQLite 暂存并去重，输出分片、变更词表和清单。日更文件先完整验证再切换版本，保留上一版本以便回退。源文件缺口显示起止日期，补齐后重放；只发布发生变化的分片。未完成全量历史导入时维持“重点词试用”标识。
- [ ] 新建 `workbench/packages/title-audit/jobs.ts` 并接入 `workbench/apps/jobs/src/index.ts` 的现有调度。每日查询源文件，发现新增申请、注册、状态变化、运营新录入的下架词或有案号的相关案件，即按新旧词中的一个已索引词召回在售标题，再做整词组检查；授权过期只重查对应范围。若规则变化无法限定关键词，则登记全量复扫。每周全扫分批运行，用主键游标恢复。
- [ ] 单份运行按店铺、市场、触发源及版本登记唯一任务，分片设置租约、重试和恢复点。以店铺、SKU、标题版本、权利或规则和证据版本去重提醒；同一问题连续出现更新已有待办，新的关键证据可以重新打开已处理项。保留“什么时候查过、当时为什么观察、今天为什么升级”。
- [ ] 待办可按店铺、级别和词筛选，点品牌词可查看所有受影响 SKU。运营可以登记误报及原因、授权及截止日、已提交改名、转法务。后台重新取得新标题并通过检查后关闭整改项。店铺访问沿用工作台现有权限，只有有权限的运营能维护本店凭据或案件。

## 上线验收与速度目标

| 项目 | 试点验收办法 |
|---|---|
| 识别是否有效 | 留出组中，每个确认因品牌表达下架的原标题均应进入复核并圈对词；单列整改后的标题被再次标高的数量。同时随机抽至少 50 个在售标题人工复核，分别统计漏报、误报和高优先级命中准确数／总数。样本量与分子分母同时汇报，漏掉确认下架案例先修规则再放量 |
| 新标题 | 试点配置下提交 100 条有代表性标题，记录冷启动和热缓存耗时；热缓存单条预检 P95 目标 ≤2 秒。上架后变更以 Amazon API 可读为起点，正常负载下 60 分钟内进入工作台；数据源延迟单列 |
| 老标题 | 构造一条从未命中过的多词品牌，标题保持不动，模拟新申请、转注册和同类商品的真实通知。验证所有相关 SKU 被找回、无关 SKU 不升级、历史记录可查。同一更新重复投递不新增重复告警。新词库版本发布后，试点受影响 SKU 目标 1 小时内入队并完成检查 |
| 覆盖与恢复 | 按 1 万条单店标题测全扫，词库已就绪后内部处理目标 ≤1 小时，另报等 Amazon 和下载的时间。周报显示完成、失败、缺失、待处理之和与应扫总量相符。模拟 429、分页中断、半份报告、词库缺日、服务重启和重复任务，验证补扫与旧版本保留 |
| 测试及放量 | 在 `workbench/tests/integration/title-audit.test.ts` 覆盖上述核心回归，在 `workbench/tests/e2e/title-audit.spec.ts` 验证“粘贴→命中→看证据→提交改名→复查”。在 workbench 运行 `pnpm exec vitest run tests/integration/title-audit.test.ts`、`pnpm exec playwright test tests/e2e/title-audit.spec.ts`、`pnpm typecheck` 与 `pnpm run check:workers`，预期均通过。单店至少跑通一次真实日更与一次全量复扫后，再逐店开启 |

**交付时间口径**　假设一名熟悉工作台的工程师、运营可提供样本、已有店铺授权与可定时运行的机器。目标第 1–2 个工作日交付重点词预检，第 3–5 个工作日跑通单店定期复查试点。完整历史库上线日期由首日下载和导入实测决定。进度汇报只列当前覆盖范围、已扫／应扫数、需优先复核数、实际耗时及阻塞项。
