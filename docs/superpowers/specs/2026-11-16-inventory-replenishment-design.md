# JIT / J1T 虚拟库存自动补库规格

依据：用户 2026-11-16 在当前聊天中的业务答复及两次范围确认。本文件优先于此前交接文档中的加扣库示例。

## 已确认规则

- 库存权威来源：用户明确“以 API 为准”。按 SP-API 的 `fulfillableQuantity`（库存报告对应 `afn-fulfillable-quantity`）计算；不使用总库存或预留量代替可售量，不要求与 Seller Flex 页面数值一致。该确认不改变当前联调模式或自动开启真实上传。

- 本期只做 RECEIVE，不做 REMOVE；加库表示增加系统可售配额。
- 当前 Seller Flex 界面对应的店铺与仓库作为一个绑定执行范围，不要求运营维护多店、多仓规则；后台仍保存上下文身份，避免其他界面的设备误领任务。
- SKU 按现有日报规则忽略大小写识别，先 J1T、再 JIT，无业务例外。原 SKU 文本保留。
- 目标是可售库存 5 件：1–4 补到 5，>=5 不操作。
- 0 库存仅纳入出过单或新上架的 SKU；老商品从未出单且为 0 的不补。
- 首次纳入启用时最近 7 天创建的新品，之后检测新增。使用平台创建时间，不把首次扫描发现的历史老商品误认成新品。新品纳管资格记录在 SKU 底账，供后续巡查使用。
- 亚马逊禁售/停售优先跳过。单纯缺货或新刊登尚未可售不等于禁售；关闭/抑制原因不明时先待核对。
- 用户进一步确认：图片问题不影响补库。当前可购买、可搜索且无禁售/抑制动作的 SKU，即使返回图片链接 404（300404），仍按 API 可售量补到 5；不处理图片修复。该确认不覆盖明确的禁售、停售或抑制状态。
- JIT 和 J1T 使用相同规则。无销量预测、实物供给、库容、体积、每日件数预算、人工覆盖或消息通知。
- 默认每 60 分钟巡查，管理员可调整间隔；仅管理员可改规则。
- 明确失败后的重试最多 3 次，每次至少间隔 120 秒；即首次尝试加最多 3 次重试。仍失败只暂停对应 SKU。
- ERP 在插件离线期间继续持久化巡查和待补需求。恢复后同一库存范围按最新读数重算，不累加几次巡查的历史差量。
- 插件可运行于其他电脑。待补需求持久化于 ERP 服务端，插件本地仅缓存正在执行任务和未确认回执。

## 首次与日常范围

启用时点固定为 enabledAt，不因每次巡查、修改间隔或重启而滑动。新品起点为 enabledAt - 7 天；以后新增 SKU 的平台创建时间必须落在该起点之后、当前观察时间之前。历史订单的“出过单”资格可单独登记，扫描从未见过不代表从未出单。缺少订单和创建证据的零库存 SKU 标为待核对，不推断补库资格。

## 数据与执行设计

ERP 用 source 适配器读取包含精确 SKU、可售量、状态、订单资格及创建时间的快照；完整性由适配器负责。来源读取失败、不完整或数据无效均保留巡查错误，不把遗漏 SKU 当 0。店铺/仓库/库位是后台上下文字段，不新增运营配置负担。

底账分别记录：规则、巡查与快照、每个库存范围的最新需求、领取与提交尝试、幂等事件。巡查和任务领取分开：离线每小时保存需求，真正领取时把当前需求批成文件。

领取后仍须在上传前核对最新可售量和禁售状态，重新计算 5-current；禁止合并历史 quantity。进入 SUBMITTING 前登记稳定文件名、文件行映射与内容摘要。提交状态未知时不自动重发；明确失败才进入两分钟重试队列。

同一范围只能有一个活动尝试。CLAIMED 超时可安全收回；SUBMITTING/SUBMITTED 超时只转待核对。成功行在库存得到执行后证据前保留对账锁，防止旧快照再次触发。失败行单独计数，其他行继续执行。

既有 818 行批次：用户确认有效 818 行全部成功；平台 819–1415 的 597 个错误对应用户清空的尾行。尾行残留格式/单元格记录是合理解释，尚未重现验证。该历史文件不进入自动补跑队列。新制表从有效业务行创建新文件，不复用旧工作簿占用范围。

## 本轮实现边界

先实现独立的 ERP 补库规则、D1 持久化任务状态机及模拟执行端，使用独立 SQLite 测试库验证数据库约束与故障恢复。不会部署、启用真实巡查或上传 Amazon。

该段记录核心阶段的边界；后续已部署只读巡查、管理界面、设备配对与最多两行的真实试跑，见 `workbench/docs/2026-11-16-库存联调接入说明.md`。用户明确以 API 可售库存为准，不要求页面数值一致；已执行一行 +3 的真实上传并收到平台零错误回执，全量自动加库仍关闭。

## 验收场景

1. 1–4 件精确补差；>=5 不动；非 JIT/J1T 不动。
2. 零库存已出单补 5；首次最近 7 天新品与后续新增补 5；历史无单零库存不补；缺少资格证据待核对。
3. 禁售优先；源异常和缺字段不创建任务。
4. 离线三轮：同 SKU 3→2→1，仅保留一份最新需求 4 件；重连前变为 4，最终仅补 1。
5. 重复巡查不覆盖较新快照，两个设备不能同时领取同一库存范围；进程重新打开数据库仍能继续。
6. 文件提交未知不重新领取，迟到回执可对账；成功但旧快照未更新时不重复补。
7. 明确失败按 2 分钟间隔最多重试 3 次，耗尽只暂停对应 SKU；重复结果不重复计数。
8. 一个文件内部分成功时，成功行保持对账、失败行单独重试；不得整文件重发。

## 本地实现与验证结果

已新增 `workbench/packages/inventory-sync/rules.ts`、`queue.ts`、`receive-file.ts`，以及 `workbench/migrations/0041_inventory_replenishment.sql`。迁移只在独立测试库中执行，没有应用到生产或日常开发数据库。

- 补库资格底账独立保存首次订单/新品证据所对应的 scanId，后续数据缺少历史字段不会抹掉资格。
- 巡查原始观察和最新需求分别保存；较旧观察不覆盖较新需求。完整快照发布前分批暂存，缺页快照不发布。
- 数据库唯一约束保护活动库存范围。测试覆盖两个领取者、错误租约、续租、未提交过期、已提交未知、迟到成功、重复结果和部分成功。
- 文件登记必须提供 `preflightId + sha256 + rows`；服务端重新计算规范 CSV、校验业务行和数量，并保存文件实际顺序。核对版本变化后，旧文件不能登记。
- 新文件仅由有效行生成，不读取旧 Excel 已用区域。CSV 行映射是物理行号（含表头）；Amazon 错误报告是否以数据行编号仍需真实模板联调确认，不擅自换算。
- 明确失败首次加三次重试，间隔 120 秒；成功后连续失败计数清零。服务端数据库关闭后重开仍能领取积压需求。
- 默认 60 分钟并支持管理员修改间隔；当前是 `due()` 判定核心，**尚未挂入线上 Cron**。

验证：2026-11-16，24 项新增行为/数据库/制表测试；全仓库 `pnpm test` 为 34 文件、266 测试通过，`pnpm typecheck` 通过，新增文件 Biome error-level 检查通过。数据库测试使用真实 SQLite 执行 SQL，不等同于线上 D1/Worker 联调。

后续工程接入点：

1. 真实 SP-API/Seller Flex 来源适配（订单资格、新品创建时间、禁售状态、可售数量）；当前测试使用模拟观察，未新发起真实 API 查询。
2. 后台自动绑定当前界面上下文，数据适配器按 SKU 汇总可售量并确定唯一补入范围，避免把每个库位各自补到 5；无需让运营维护多仓规则。
3. 管理设置、设备配对及鉴权 HTTP 接口、Worker 定时接线、库存任务视图。
4. 插件领单、上传、结果采集和错误文件行号换算。当前结果函数接收经过核实的行级结论，不能直接把文件 Completed 当作所有行成功。
5. 当前对账核心采取保守策略：成功后读到目标量才解除对账锁。如果提交后又产生新销量、回读低于 5，需要在真实来源适配阶段增加已发生增量/新销量证据的对账支持；不能用旧报表强行解锁，也不能把这一限制带到正式自动运行。

因此，本轮完成的是本地补库核心与模拟执行测试，尚未完成线上库存自动补充。
